  <div class="sechead">

    <h1>System Architecture</h1>
    <p class="sechead__sub">Audit of one product across four frontend surfaces, one Python backend, and a shared design system. Generated 2026-08-25 against commit <code>9984869</code>.</p>
  </div>

  <p class="lede">BillGen is a Belgian invoicing SaaS with a finished domain core and an unfinished product wrapper. This document separates those two facts, measures each, and orders the work.</p>

  <div class="grid g3">
    <div class="stat">
      <p class="stat__k">Product areas</p>

      <p class="stat__n">21 wired · 30 partial · 63 none</p>
    </div>
    <div class="stat">
      <p class="stat__k">Missing capabilities</p>
      <p class="stat__v" style="color:var(--gap)">171</p>
      <p class="stat__n">distinct backend gaps</p>
    </div>
    <div class="stat">
      <p class="stat__k">Library components</p>
      <p class="stat__v">72</p>
      <p class="stat__n">35 mounted · 26 never rendered</p>
    </div>
  </div>

  <div class="note">
    <p><strong>The central finding.</strong> Layer 1 — the invoicing core — has <em>zero</em> unwired areas. Everything outstanding is the SaaS wrapper around it. The engineering half of the 2026 audit closed; the commercial half never started. That is a coherent position to be in, and it is not the same as being 18% finished.</p>
  </div>

    <li><strong>The endpoint inventory</strong> — read directly from <code>api/routers/</code>, not from documentation.</li>
    <li><strong>The component matrix</strong> — computed by walking JSX across all frontends plus the Studio AI reference.</li>
    <li><strong>The Studio AI reference</strong> — <code>docs/billgen---enterprise-invoicing-&amp;-financial-saas.zip</code>, 95 files. A Google AI Studio (Gemini) generation dated 2026-08-25, seeded with this project&#39;s stylesheets but importing none of its components — see <a href="#repo">§15</a>.</li>

  <h3>The multi-layer navigation model</h3>
  <p>The reference makes a navigation pattern explicit that the current build only half implements. It has three depths, and each depth answers a different question:</p>

  <div class="tw">
    <table>
      <thead><tr><th>Depth</th><th>Question it answers</th><th>Mechanism</th><th>State</th></tr></thead>
      <tbody>
        <tr><td><strong>N1</strong> Primary</td><td>Which part of the business am I in?</td><td class="ev">Top bar, one entry per primary section, each opening a popup list of its sub-pages</td><td><span class="chip c-done">shipped</span></td></tr>
        <tr><td><strong>N2</strong> Section</td><td>Which slice of this section?</td><td class="ev">Per-page sub-navigation: <code>Tabs</code> with counts on lists, <code>SettingsShell</code> rail on settings</td><td><span class="chip c-partial">partial</span></td></tr>
        <tr><td><strong>N3</strong> Record</td><td>What is true of this one record?</td><td class="ev"><code>Drawer</code> inspector — metadata, financials, <code>StatusTimeline</code>, actions</td><td><span class="chip c-gap">gap</span></td></tr>
      </tbody>
    </table>
  </div>

  <details>
    <summary>N1 — the sidebar decision that needs making</summary>
    <div class="det-body">
      <p>The reference uses a persistent dark sidebar with 11 destinations grouped under <em>Menu Principal</em> and <em>Configuration &amp; Fiscalité</em>, each carrying a count badge (overdue invoices, quote count, customer count).</p>
      <p>The current build deliberately deleted its sidebar in favour of TopNav-only navigation with five destinations. Both are defensible; they are not compatible. The reference's model scales to the 15-section IA far better, and the count badges are real signal. Adopting it means reversing the earlier decision, which is a product call.</p>
      <p><code>SidebarNav</code> exists in the library with <code>category</code> and <code>badge</code> support already in its props — so the component cost of switching is close to zero.</p>
    </div>
  </details>

  <details>
    <summary>N2 — what the section sub-navigation should carry per section</summary>
    <div class="det-body">
      <p>Invoices already does this correctly: six status tabs, each with a count, backed by the server-side <code>?status</code> filter. The pattern generalises:</p>
      <ul>
        <li><strong>Sales → Invoices</strong> — Toutes / Brouillons / Émises / Payées / Partiellement payées / En retard / Annulées <span class="chip c-done">built</span></li>
        <li><strong>Sales → Quotes</strong> — All / Draft / Sent / Accepted / Refused / Expired / Invoiced <span class="chip c-gap">no backend</span></li>
        <li><strong>Clients</strong> — All / Active / Archived / Missing VAT / Missing address <span class="chip c-gap">needs filters</span></li>
        <li><strong>Catalog</strong> — Products / Services / Categories / Pricing / VAT / Archived <span class="chip c-partial">derivable, unfiltered</span></li>
        <li><strong>Reports</strong> — Revenue / Invoices / Payments / Outstanding / Overdue / VAT / Export <span class="chip c-partial">3 of 7 wired</span></li>
        <li><strong>Settings</strong> — the <code>SettingsShell</code> rail, 15 sections <span class="chip c-partial">rail built, sections stubbed</span></li>
      </ul>
      <p>Counts on N2 tabs must come from the server. Computing them by fetching every record and counting in the browser works at demo scale and fails at customer scale.</p>
    </div>
  </details>

  <details>
    <summary>N3 — the record inspector, currently missing entirely</summary>
    <div class="det-body">
      <p>The reference implements <code>InvoiceDrawer</code> and <code>CustomerDrawer</code>: a right-hand panel carrying identity, status badge, metadata, financials, copyable identifiers, a status timeline, and the action cluster.</p>
      <p>This is the single highest-value structural pattern in the reference, because it also solves the "action soup" problem — five equal-weight buttons per table row move into the drawer, and the row keeps one primary action plus an overflow menu.</p>
      <p><code>Drawer</code>, <code>StatusTimeline</code>, <code>CopyButton</code>, <code>ConfirmDialog</code> and <code>Menu</code> are all built and none are rendered anywhere in the shipping app.</p>
    </div>
  </details>

  <h3>Token divergence — a decision, not a bug</h3>
  <div class="note">
    <p><strong>Decided 2026-08-25 — <code>tokens.css</code> is the standard.</strong> The reference kept <code>--brand-emerald-500</code> in the palette but repointed <code>--bg-accent</code> at <code>--brand-blue-500</code> <code>#2563EB</code>, and swapped Satoshi for Plus Jakarta Sans. That re-skin is <strong>rejected</strong>: emerald <code>#10B981</code> and Satoshi remain canonical, and the reference contributes layout and component patterns only — never palette or type.</p>
    <p>Enforced rather than documented: <code>frontend-react/src/scaffold/tokens.test.ts</code> fails the build if the accent stops being emerald, the sans face stops being Satoshi, or any Tailwind colour utility or raw hex reaches app or component source. The four violations that existed — <code>text-blue-700</code> and <code>text-gray-500</code> on the auth screens — are fixed.</p>

  <details>
    <summary>Why Peppol is the highest-leverage compliance item</summary>
    <div class="det-body">
      <p>Belgium mandates structured e-invoicing for B2B from 2026. BillGen already produces Helger-validated Peppol BIS 3.0 XML carrying the Belgian elements — EndpointIDs, OGM-VCS structured communication, KBO legal identifier, party contact — layered over the EN 16931 multi-rate engine.</p>
      <p><strong>Every part of that is done and none of it ships.</strong> The file is generated and downloaded by hand because no Access Point transmits it. This is the one place where a single integration converts finished, tested work into a headline market capability. It is not a settings toggle; treat it as a product surface.</p>
      <p>Round-trip through a real Access Point remains untested — schematron validation has passed on BE and non-BE samples, which is necessary and not sufficient.</p>
    </div>
  </details>

  <details>
    <summary>Cookie consent — currently compliant by accident</summary>
    <div class="det-body">
      <p>No analytics run anywhere in the product today. That is the only reason the absence of a consent mechanism is not already a violation. The moment any analytics, session recording, or marketing pixel is added, <code>CMP-04</code> becomes blocking rather than pending.</p>
      <p>Build the consent layer <em>before</em> the first analytics call, not after.</p>
    </div>
  </details>

    <p>One endpoint. Converts six <a href="#status">Company areas</a> from write-once to editable, and removes the most visible defect in the product — a permanent VAT typo. Every field already exists on the model. See <a href="#backend">§04</a>, <code>BGEN-API-01</code>.</p>
  </div>

  <div class="sprint">
    <div class="sprint__h"><span class="sprint__n">STEP 2</span><span class="sprint__t">Expose the rules that already exist</span></div>
    <p><code>GET /vat-rates</code>, <code>GET /pdf-templates</code>, identifier validation. Pure plumbing over finished Python, and it removes hardcoded VAT rates from the frontend — a correctness risk, not a convenience. See <a href="#backend">§04</a>, <code>BGEN-API-04</code>.</p>
  </div>

  <div class="sprint">
    <div class="sprint__h"><span class="sprint__n">STEP 3</span><span class="sprint__t">Build the VAT report</span></div>
    <p>The highest user value available. For the target customer this is the reason to own the software, and every input is already in the database. See <a href="#roadmap">Sprint 2</a>.</p>
  </div>

  <div class="sprint">
    <div class="sprint__h"><span class="sprint__n">STEP 4</span><span class="sprint__t">Start email transport (B1)</span></div>
    <p>Longest lead time and widest fan-out, so start it early and in dependency order: provider → password reset → verification → send-invoice → reminders. See <a href="#roadmap">Sprint 3</a>.</p>
  </div>

    <div class="sprint__h"><span class="sprint__n">STEP 5</span><span class="sprint__t">The three brand decisions — all settled</span></div>

      <li class="done"><b>BGEN-BRAND-03</b> — decided: one custom SVG grammar, enforced by a guard test</li>
    </ul>

Items L6-01 through L6-03 — panel styling, heading weight, button contrast — are hours of work and change the perceived quality of every screen in the product.</p>

  <h3>Reading the diagram</h3>
  <p>The load-bearing claim is band 2. <code>ia.ts</code> is not documentation — it is a typed registry that the router, the navigation and the status badges all read at runtime. A product area that is not a node in that file cannot be reached in any frontend, and a node marked anything other than <code>wired</code> renders through the deliberately-ugly scaffold kit so unbuilt surface can never be mistaken for finished work.</p>

  <p>Bands 3 to 5 are the rule the whole backend is organised around, recorded in <a href="ADR-0001-three-layer.md">ADR-0001</a>: <strong>dependencies point inward and never back out.</strong> <code>core/</code> imports no framework — no FastAPI, no SQLAlchemy — which is why the 219 tests run without a server or a database. <code>api/</code> may import <code>core/</code>; <code>core/</code> may not import <code>api/</code>. Persistence is reached through abstract ports in <code>core/repository/</code>, which is what lets the same domain code run against SQLite on the desktop and Postgres in the cloud.</p>

  <p>The two facts worth carrying away from band 6: nothing in the product sends anything to anyone, and nothing stores a file. Every gap that looks like a missing screen in §14 resolves to one of those four boxes.</p>

  <div class="note note--warn">
    <p><strong>The path that stops short.</strong> Follow the Peppol rail. <code>core/einvoicing/ubl_builder</code> produces BIS 3.0 XML that passes Helger validation, <code>GET /invoices/{id}/peppol.xml</code> serves it, and the user downloads a file. In a finished product that file is transmitted to an access point and the invoice is legally delivered. Here the flow ends at the browser's download folder. The engineering is done; the last hop was never built.</p>
  </div>

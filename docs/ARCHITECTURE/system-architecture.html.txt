System Architecture
===================

Audit of one product across four frontend surfaces, one Python backend, and a shared design system. Revised 2026-08-28 against commit 748fd2c — the last code commit, since a document cannot name the commit that contains it.

BillGen is a Belgian invoicing SaaS with a finished domain core and an unfinished product wrapper. This document separates those two facts, measures each, and orders the work.

What changed since v0.10 (2026-08-27). Quotes shipped with their own numbering
 series, and the last report gaps closed — /alerts, /search,
 /vat-treatment, and the payments, clients and products reports. Two features were
 scaffolded and deliberately left unwired (§18), and a parallel
 audit engine was built from the specification in docs/
 (§19). Backend tests 392 → 423; the surface is now
 108 endpoints across
 26 routers.

And this document stopped being hand-maintained where it kept going wrong. The
 audit engine found eight endpoints documented here that no longer existed and fifty that were never
 written down. The endpoint inventory and every volatile count are generated now
 (§19); the judgements are not.

The central finding, restated. Layer 1 — the invoicing core — still has zero unwired areas. What has changed is the commercial half: it is no longer unstarted. The entitlement layer means the server can now price, meter and refuse, tier by tier. Nothing renders it yet. So the shape of the problem has moved from “the backend cannot answer this” to “no screen asks” — and that is frontend work, not architecture.

The multi-layer navigation model

The reference makes a navigation pattern explicit that the current build only half implements. It has three depths, and each depth answers a different question:

N1 Primary · Which part of the business am I in?
    Mechanism: Top bar, one entry per primary section, each opening a popup list of its
    sub-pages
    State: shipped

N2 Section · Which slice of this section?
    Mechanism: Per-page sub-navigation: Tabs with counts on lists, SettingsShell rail on
    settings
    State: partial

N3 Record · What is true of this one record?
    Mechanism: Drawer inspector — metadata, financials, StatusTimeline, actions
    State: gap

The reference uses a persistent dark sidebar with 11 destinations grouped under Menu Principal and Configuration & Fiscalité, each carrying a count badge (overdue invoices, quote count, customer count).

The current build deliberately deleted its sidebar in favour of TopNav-only navigation with five destinations. Both are defensible; they are not compatible. The reference's model scales to the 15-section IA far better, and the count badges are real signal. Adopting it means reversing the earlier decision, which is a product call.

SidebarNav exists in the library with category and badge support already in its props — so the component cost of switching is close to zero.

Invoices already does this correctly: six status tabs, each with a count, backed by the server-side ?status filter. The pattern generalises:
  - Sales → Invoices — Toutes / Brouillons / Émises / Payées / Partiellement payées / En retard / Annulées built
  - Sales → Quotes — All / Draft / Sent / Accepted / Refused / Expired / Invoiced no backend
  - Clients — All / Active / Archived / Missing VAT / Missing address needs filters
  - Catalog — Products / Services / Categories / Pricing / VAT / Archived derivable, unfiltered
  - Reports — Revenue / Invoices / Payments / Outstanding / Overdue / VAT / Export 3 of 7 wired
  - Settings — the SettingsShell rail, 15 sections rail built, sections stubbed

Counts on N2 tabs must come from the server. Computing them by fetching every record and counting in the browser works at demo scale and fails at customer scale.

The reference implements InvoiceDrawer and CustomerDrawer: a right-hand panel carrying identity, status badge, metadata, financials, copyable identifiers, a status timeline, and the action cluster.

This is the single highest-value structural pattern in the reference, because it also solves the "action soup" problem — five equal-weight buttons per table row move into the drawer, and the row keeps one primary action plus an overflow menu.

Drawer, StatusTimeline, CopyButton, ConfirmDialog and Menu are all built and none are rendered anywhere in the shipping app.

Token divergence — a decision, not a bug

Decided 2026-08-25 — tokens.css is the standard. The reference kept --brand-emerald-500 in the palette but repointed --bg-accent at --brand-blue-500 #2563EB, and swapped Satoshi for Plus Jakarta Sans. That re-skin is rejected: emerald #10B981 and Satoshi remain canonical, and the reference contributes layout and component patterns only — never palette or type.

Enforced rather than documented: frontend-react/src/scaffold/tokens.test.ts fails the build if the accent stops being emerald, the sans face stops being Satoshi, or any Tailwind colour utility or raw hex reaches app or component source. The four violations that existed — text-blue-700 and text-gray-500 on the auth screens — are fixed.

  - @google/genai — an AI SDK with no corresponding UI in the reference. Dead weight; do not adopt.
  - canvas-confetti — celebratory micro-interaction. Optional; costs 4 KB.
  - motion 12.x — the current system does motion in CSS tokens. Adding a JS animation library duplicates that.
  - lucide-react — worth considering only as a wholesale replacement for the 14 custom icons, not alongside them.
  - express — the reference serves itself; irrelevant here, the API is FastAPI.
  - No router and no state library. The reference switches views with useState. The SaaS app uses react-router and TanStack Query — strictly better; do not regress.

The four hard blockers

B1 · No email transport
    Class: Cloud & integrations
    State: gap
    Fan-out: Reminders, send-invoice, invitations, verification, password reset, support
    tickets, notification mail. Highest fan-out in the product.

B2 · No blob storage
    Class: Architecture
    State: gap
    Fan-out: All 7 Documents areas, branding/logo, invoice attachments, client documents,
    document search. Company.logo_key already dangles.

B3 · No PATCH /companies/{id}
    Class: Data & persistence
    State: done
    Fan-out: Shipped — GET + PATCH /companies/{id}, every model field editable except
    logo_key (B2). The router re-validates the merged model, so an explicit null on a
    non-nullable field is a 422 rather than silent corruption.

B4 · No subscription/plan model
    Class: Business logic
    State: server done
    Fan-out: Shipped 2026-08-26 — see §16. Four sellable tiers and one granted, six meters,
    atomic quota guards, a uniform 402, and PdfService(branded=…) honouring
    pdf_remove_branding. What is left is a checkout provider (deliberately deferred) and
    every screen: no meter, badge or upgrade path renders yet.

These are the cheapest wins on the board — the Python exists and works, only the HTTP surface is absent.

Belgium mandates structured e-invoicing for B2B from 2026. BillGen already produces Helger-validated Peppol BIS 3.0 XML carrying the Belgian elements — EndpointIDs, OGM-VCS structured communication, KBO legal identifier, party contact — layered over the EN 16931 multi-rate engine.

Every part of that is done and none of it ships. The file is generated and downloaded by hand because no Access Point transmits it. This is the one place where a single integration converts finished, tested work into a headline market capability. It is not a settings toggle; treat it as a product surface.

State the gap precisely, because this document has stated it loosely. The open
 question is not whether the XML is correct — the predecessor demo's PDF → Peppol path was
 exercised with a real user, and schematron passes here on BE and non-BE samples. The gap is
 transmission from inside the application: sending over the network the way a bank's
 billing app does, rather than producing a file a human then hands to a portal like Doccle. Those are
 different products to the person using them, and only the second one exists today.

Two things that follow, and neither is a coding task. You do not have to be an Access
 Point. Resellers (Storecove, Ecosio, Unifiedpost) turn an existential interoperability risk
 into a procurement decision — and their per-document price then sets the gross-margin floor, which
 means it sets BillGen's price. Onboarding one is calendar-bound, not code-bound: a
 contract, KYC, SMP registration and a company number, measured in weeks of somebody else's queue. It
 is therefore a clock to start in parallel with everything on the roadmap below, and it cannot be
 sequenced after any of it.

No analytics run anywhere in the product today. That is the only reason the absence of a consent mechanism is not already a violation. The moment any analytics, session recording, or marketing pixel is added, CMP-04 becomes blocking rather than pending.

Build the consent layer before the first analytics call, not after.

MVP Scope

Fixed 2026-09-02. Deliberately unnumbered — it cuts across the roadmap rather than sitting at a point on it. The smallest product worth putting in front of a paying Belgian business.

Production Readiness & Security
-------------------------------

The layers that are invisible from the frontend. Not a checklist to tick once — the set of properties a new feature must not break.

Why this section exists, and why it is not a checkbox list. The naive model of a web application is two boxes: frontend, backend.     State: gap

How to use this section when adding a feature. These rows are guardrails, so the question is never “have I ticked them” but “does what I am about to build break one”:
  - Does it read or write data? It goes through a repository port. Not for tidiness — that port is what makes SEC-01 and SEC-17 true, and a raw-SQL shortcut silently repeals both at once.
  - Does it take longer than a request should, or call anyone external? It needs PROD-07, which does not exist yet. Say so, rather than putting it in a handler.
  - Does a machine produce output a person reads? It enters the ai_transparency registry before it ships, with its tier and its drift path (AI-01, AI-02).
  - Does it score a person rather than classify a transaction? Stop. That is Annex III, a conformity assessment, and a different product timeline (AI-05).
  - Does it add a dependency, a secret, or an environment variable? SEC-13 and SEC-14 — and the field exists in Settings before it appears in .env.example, never the other way round.
  - Does it store personal data, or a new kind of document? core/trust/personal_data.py gains a row with a purpose, a basis and a retention, or SEC-12 gets quietly worse.

A status in this section with no evidence — a path, a command, an endpoint — is an opinion, not a status. And staleness runs both ways: six rows above described a weaker system than the one that exists, which is how a downstream analysis inherits a defect that was already fixed.

Data Architecture
-----------------

One request, end to end — which file touches it, in what order, and where it stops.

Sections §02 and §04 list the parts. This one shows the path between them: what a click becomes, which directory owns each hop, and which hops do not exist yet.

Reading the diagram

The load-bearing claim is band 2. ia.ts is not documentation — it is a typed registry that the router, the navigation and the status badges all read at runtime. A product area that is not a node in that file cannot be reached in any frontend, and a node marked anything other than wired renders through the deliberately-ugly scaffold kit so unbuilt surface can never be mistaken for finished work.

Bands 3 to 5 are the rule the whole backend is organised around, recorded in ADR-0001: dependencies point inward and never back out. core/ imports no framework — no FastAPI, no SQLAlchemy — which is why the 298 tests run without a server or a database. api/ may import core/; core/ may not import api/. Persistence is reached through abstract ports in core/repository/, which is what lets the same domain code run against SQLite on the desktop and Postgres in the cloud.

The two facts worth carrying away from band 6: nothing in the product sends anything to anyone, and nothing stores a file. Every gap that looks like a missing screen in §14 resolves to one of those four boxes.

The path that stops short. Follow the Peppol rail. core/einvoicing/ubl_builder produces BIS 3.0 XML that passes Helger validation, GET /invoices/{id}/peppol.xml serves it, and the user downloads a file. In a finished product that file is transmitted to an access point and the invoice is legally delivered. Here the flow ends at the browser's download folder. The engineering is done; the last hop was never built.

----------------------

What each plan may do, where that is decided, and what still has no screen.

The one architectural rule. api/entitlements/matrix.py is the only place a tier name maps to a capability, and core/ may not import it. The domain knows how to create an invoice; this layer decides whether the caller's subscription permits the call. That separation is what lets a price or quota change ship without touching domain code — and it is the same inward-pointing dependency rule as ADR-0001, applied to commerce.

What is deliberately not an upsell. Credit notes, PDF export, backup, restore and legacy import are on every tier including Free. Correcting an invoice and owning your own data are not features to be sold — a free user who cannot issue a credit note has been handed a legal problem, and a free user who cannot export has been locked in. Peppol export is universal for the same reason: Belgium mandates structured e-invoicing for B2B from 2026, and metering the volume is legitimate where withholding the capability is not.

The four design decisions worth keeping

E-01 · Usage is derived, never accumulated
    Why it is built this way: Every meter is a COUNT(*) over rows that already exist,
    filtered on created_at for flow meters. There is no counter column, so there is no
    counter to drift: a restore, a legacy import, a deleted draft or a manual DB fix all
    move the number correctly and automatically. An incremented counter would need repairing
    by hand after any of those. Peppol documents are the one meter with no table of their
    own and are counted from the append-only audit log.

E-02 · 402 means commercially unavailable; 403 means not authorized
    Why it is built this way: One uniform body — error, required_tier, feature, message —
    and isEntitlementError(err) on the client. Only a 402 may open an upgrade modal. The
    consequence for the frontend is strict: one handler at the query boundary, and no
    per-feature payment logic anywhere in React.

E-03 · Quotas refuse creation only
    Why it is built this way: Reading, editing, exporting or correcting something that
    already exists is never refused for a quota reason. An over-limit tenant keeps every
    record; only new creation stops. A customer's own business records are not put behind a
    paywall — which is also what makes a lapsed subscription a survivable state rather than
    a hostage situation.

E-04 · The allowance is spent at draft creation, not at issue
    Why it is built this way: Issuing is legally load-bearing — it consumes a gapless number
    and produces a document with statutory force — so it must never fail for a commercial
    reason. Charging the slot to the draft moves the refusal to the harmless end of the
    lifecycle. A deleted draft frees its slot, which E-01 makes automatic.

quota_guard is a context manager that takes a row lock on the organization before counting and holds it until the endpoint body's own transaction has landed. Without it the naive shape — read 49, return, create, and someone else also read 49 — lets two concurrent requests both create the 50th invoice. Every quota check for one tenant serialises on that single row; different tenants never contend.

It is unproven. with_for_update() is a no-op on SQLite — one connection behind a StaticPool, which is what both the desktop build and the entire test suite run on. It becomes a real FOR UPDATE only on Postgres. The CI workflow runs the Python suite twice, once on each, and CI has never executed because the repo has never been pushed (BGEN-OPS-01). The same asymmetry, for the same reason, applies to the gapless numbering lock. A red first run would be information, not a regression.

Decisions of Record
-------------------

Four rulings this document had no section for. The board is ROADMAP_IA.md; this is the summary an architecture reader needs.

Three were taken on 2026-08-27 and one is the correction that produced them. They are here
 because each one changes how a number elsewhere in this document should be read.

§11b — the navigation is not the coverage map

Until this session, routableNodes() generated the router straight from ia.ts,
 so a node exists and a node is a destination were one statement. That was correct while
 the product was half-built: SectionIndex counting wired areas and ScaffoldPage
 naming the endpoint each gap waits for are build-time instruments, and they earned their
 place. They stop earning it as the gaps close. Company was the proof — nine nav entries over one
 PATCH against one row.

The rule. A nav destination is a place you go before you know which record
 you want. Anything that only means something after you have picked one belongs inside that
 record. Not “remove the repetition” — repetition is the symptom; the cut is list vs
 record.

The mechanism, and why it does not move any number above. IaNode gained
 nav?: boolean and mergedInto?: string. A hidden node keeps its path, its status
 and its place in coverage(); it loses only the door, and mergedInto makes the old
 URL redirect rather than 404. routableNodes(), coverage() and
 missingEndpoints() still read the whole tree, which is why §01
 counts 114 leaves with 15 of them curated out of the nav. A guard test asserts exactly that: curating must
 never change a coverage number.

Applied to two sections, proposed for ten. Company is 9 entries → 1 (the section
 landing is the record, and the three areas blocked on a model are scaffold blocks inside it).
 Clients is 7 → 3. The remaining sections have a written proposal in §11b — roughly 100 nav
 entries down to 45 — and are built by nobody pending a decision.

What the rule caught on its first day. “Client 360” was a
 Clients menu entry whose path is customers/clients/:clientId, so clicking it navigated to that
 literal string. Invoice detail was the same, and the command palette had the bug one layer down. Nobody had
 noticed, because the way to a record is to click a row — which is the rule, arriving as a bug before
 it arrived as a principle.

§11c — comments must not ship, and must not be deleted

The published artifact should not read as a guided tour of how the product works; the comments are also
 the reason a session can resume where the last one stopped. So: strip on export, never in the
 tree. The exposure is narrower than it looks — a private repo is unreadable, and the SaaS
 bundle is already clean because Vite minifies with esbuild and ships no sourcemap. The Electron artifact is
 the real one: app.asar unpacks trivially, and a bundled Python backend is source.

The trap: docstrings here are not comments. FastAPI and Pydantic publish them — a
 class docstring becomes the OpenAPI description, which generates api.d.ts. Strip
 # comments freely; spare schema and route docstrings or the API documents itself into silence.

§11d — what “safely deletable” means in this tree

Three jobs keep being bundled and belong apart: not writing the code (a write-time discipline),
 finding what is genuinely unused (knip / vulture — zero tokens,
 objective, repeatable), and keeping comments out of the artifact (§11c). An over-engineering
 audit pointed at this tree will flag the instruments the project is steered by: the scaffold kit, the
 never-rendered components, IA nodes with no screen, the comments, and four languages with a key guard but
 no usage guard. A deletion is safe when the guard tests stay green and the deleted thing is not one
 of those five.

Peppol — the gap is transmission, not validation

Corrected 2026-08-27, and it changes how §08 reads. The XML is not the open
 question: the predecessor demo's PDF → Peppol path was exercised with a real user, and schematron
 passes here. What does not exist is sending from inside the application rather than handing
 a file to a portal. You do not need to be an Access Point — reselling one turns the
 interoperability risk into procurement, and that vendor's per-document price sets this product's price
 floor. Onboarding is contractual and measured in weeks, so it is a clock to start in parallel with the
 roadmap, never a step sequenced after it.

Audit System
------------

A parallel engine that audits this product and this document. Added 2026-08-28.

billgen-audit/ builds
 docs/BillGen_Professional_Audit_System_Final_Specification.docx into running software. It is
 parallel, not integrated: it does not import BillGen, BillGen does not import it, and
 nothing in this repository's build, test or lint path touches it. The target is a path read as text, which
 is what lets it audit a checkout it could not even install. Standard library only. Run it with

Thirteen deterministic scanners cover the specification's phases 0–3 and 5–7 —
 discovery, the enforcement model, routes and authorization, accounting invariants, the document engine, the
 Belgian rule registry, e-invoicing, privacy, secrets, dependencies, resilience, observability, and drift

 diff. Its own 22 tests are not collected by this repository's suite, whose testpaths is
 ["tests"].

What it refuses to do

Most of the design is the specification's §1 taken literally — no hallucinated
 compliance and absence of evidence is not evidence of compliance — and each refusal is
 enforced in code rather than requested in a prompt.

A legal_requirement finding with no authoritative source cannot be constructed · findings.py raises in __post_init__

A pattern match never becomes compliance — it becomes NEEDS_CONFIRMATION · scanners/legal.py

An unassessed domain scores n/a, never 100, and the verdict is never GREEN while one is open · scoring.py

Confidence is separate from severity and discounts the penalty — a CRITICAL at 0.35 is a verification task, not a fix · findings.py · scoring.py

A secret's value is never quoted into the report, which is itself a document that gets shared · scanners/privacy.py

Dynamic testing stays off until a human passes --authorize-dynamic · config.py · cli.py

The tool was wrong three times before it was right, and that is the useful part.
 Run against BillGen, the route scanner first emitted 56 findings, roughly 50 of them false,
 because this product authenticates in one global middleware and every handler therefore looks
 unauthenticated when read one at a time. scanners/enforcement.py now detects the enforcement
 model before the route scanner runs and gates what it may claim: 56 → 4 substantive. Separately,
 Legal/VAT scored a clean 100/100 because a grep for “retention” matched a document listing
 retention as a missing feature; and a ^-anchored regex silently matched nothing, so
 the e-invoicing check reported “no generation” about a module whose whole purpose is
 generation. All three are fixed and guarded by tests. A tool with that false-positive rate is switched off
 within a day, and the findings it was right about go with it.

Work Distribution & Ownership
-----------------------------

The same work, seen by who does it rather than by what it is. A division of labour for a company of ~50 — and, read today, the order in which one person hands work away.

Why this section is not premature. Every other section answers “what is built.” This one answers “whose job is it.” Those are different questions, and the second one is the one a solo founder cannot answer from the code — because when one person does every role, the roles become invisible, and invisible roles are the ones that get skipped.

Read it three ways. As a hiring order: which function relieves the most risk per head. As an outsourcing list: which rows can be bought as a service instead of a salary. As a gap check: a function with open rows and nobody named is not understaffed, it is unowned — and unowned work does not fail loudly, it simply never happens.

The order, if money were spent tomorrow
  - DevOps — bought, not hired. Nine open rows, and most of PROD-01 to PROD-04 are managed services costing tens of euros a month. Highest risk removed per euro, by a wide margin.
  - The jurist, for the DPA and terms. Blocks B2B revenue outright. Cannot be engineered around.
  - The accountant, for the mandatory-mention sign-off. The gate is live in issue() and is a legal claim the code cannot self-certify.
  - The Peppol Access Point conversation. Not because it is urgent, but because it is slow — the queue starts when you join it.
  - Marketing content. The mandate creates the demand; someone has to meet it in writing.

The failure mode this section is really about. A solo founder does not drop roles they have decided to skip. They drop the roles they never named — and the named-but-unowned rows above (DevOps, legal, compliance, partnerships) are precisely the ones with no daily feedback. Nothing on a screen goes red when there is no rehearsed restore. The frontend, by contrast, complains the moment it is neglected, so it gets the attention.

That asymmetry is why this document appears static beside the frontend: the visible layer reports its own state and the invisible ones do not. The remedy is not discipline — it is making the invisible rows produce evidence, which is what §10 and the audit engine exist to do. A row here with no name against it is a decision, and it should be a deliberate one.

The Customer Journey, End to End
--------------------------------

Fourteen stages from the first marketing click to a deletion request. What exists, what does not, and which control each one rests on.

Why this axis, when §10 already lists the controls. A control list answers “is the system sound.” This answers a different question: can a person actually become a customer, be one, and stop being one. A product can score well on the first and be impossible on the second, and it is the second that produces revenue and the second that regulators time with a stopwatch.

Every row was checked against the routers and services, not against the roadmap. “Missing” here means grep found nothing, not that it is unplanned.

Two clocks that start without you

Most gaps above wait politely. These two do not — they begin on someone else's action, and the countdown runs whether or not anything is built:
  - Erasure — one month from a customer's request (J-14). Extendable to three with justification, but the extension itself must be communicated inside the first month.
  - Breach notification — 72 hours from awareness. none There is no incident-response plan, no notification template, and no defined “aware” moment. Note the dependency: awareness requires detection, and detection is PROD-01 and PROD-04. Without them the 72 hours start whenever someone happens to notice — which is not a defence, it is a longer breach.

Being honest about the order. Nothing in this section argues for building J-04 through J-12 before hosting exists. It argues that the gap is known and shaped, not diffuse — and that “what does a paying customer need” is a different question from “what does a 50-person company need” (§21). Both are worth answering. Only one of them is between here and the first euro.

Assurance Layer — the four review agents
----------------------------------------

How this document stops being a snapshot: four specialist reviewers, one finding schema, one orchestrator that correlates them.

Everything above was measured by hand, once, against commit 2a83ccb. That is a
 document with a half-life. This section specifies the review system that regenerates it — four
 agents with named scopes, explicit checklists and an evidence requirement, so that a re-run after any
 architectural change produces a diff rather than a fresh opinion.

Why four and not three. Legal, accounting and privacy are three professional
 perspectives on the same product; system architecture is the substrate all three make claims about. Fold
 architecture into any one of them and it inherits that agent's bias — the legal agent will call
 a missing index a compliance risk. Keeping it fourth is what lets the orchestrator say “the
 legal requirement is X, the accounting consequence is Y, and the code path that violates both is
 Z” as one finding rather than three.

AG-1 · 🇧🇪 Belgian Legal & VAT
    The one question it owns: Is what this software issues a legally valid Belgian document?
    Reads: core/rules/ (vat, belgian_legal, identifiers, numbering), core/einvoicing/,
    core/pdf/templates/, sample output
    Deliverable: Findings + a mandatory-mentions matrix per document type and language

AG-2 · 🧾 Accounting systems
    The one question it owns: Would an accountant trust these records and reconcile from
    them?
    Reads: core/services/, core/models/, lifecycle transitions, reports, exports, audit log
    Deliverable: Findings + a lifecycle state diagram with every illegal transition named

AG-3 · 🔐 GDPR / DPO
    The one question it owns: Is personal data processed lawfully, and does the code match
    the policy?
    Reads: db/ schema, api/routers/, logging, third-party calls, the legal corpus, the
    frontends' network surface
    Deliverable: Findings + a data map and a records-of-processing draft

AG-4 · 🏗️ System architect
    The one question it owns: Is it sound, secure, maintainable and recoverable?
    Reads: The whole tree, Dockerfile, infra/, CI, lockfiles, the ADRs
    Deliverable: Findings + this document, regenerated

The rule that keeps the legal agent honest

Every finding from AG-1 and AG-3 must carry one of four force values, and an agent that
 cannot choose must pick the last one:

REQUIRED · A statutory obligation, citable to a named source
    Consequence if unmet: Blocks release. Cite the article or the FPS Finance page, not a
    blog.

RECOMMENDED · Professional practice, not law
    Consequence if unmet: Roadmap item with a rationale.

PRODUCT · A design choice with no external constraint
    Consequence if unmet: Recorded in §17, argued on merits.

CONFIRM · Plausibly required; the agent is not authoritative
    Consequence if unmet: Goes to a Belgian accountant or counsel before code is written
    against it.

This is the failure mode to design against. An unconstrained agent asked “is this
 compliant?” will return every accounting convention it has ever seen, uniformly labelled as Belgian
 law, and the roadmap will fill with obligations that do not exist. The force field is cheap; without it
 the whole assurance layer is worse than no audit, because it is a confident one.

The finding schema — one shape, four producers

Findings are only correlatable if they are one record type. Evidence is a file path and a line, never a
 paraphrase: a finding that cannot point at code is a question, and questions go in a different list.

finding:
  id:            LEGAL-014            # AGENT-nnn, stable across re-runs
  agent:         legal | accounting | gdpr | architecture
  severity:      critical | high | medium | low
  force:         REQUIRED | RECOMMENDED | PRODUCT | CONFIRM   # legal + gdpr only
  category:      vat | numbering | lifecycle | consent | tenancy | resilience | …
  location:      core/services/invoice_service.py:212         # file:line, or a route
  claim:         one sentence, falsifiable
  evidence:      the code or the absence of it — quoted, not described
  requirement:   what must be true, with its source
  recommendation: the smallest change that makes it true
  confidence:    high | medium | low
  source:        FPS Finance / EN 16931 / GDPR Art. 30 / — (none, for PRODUCT)
  correlates:    [ACCT-007, ARCH-022]                          # filled by the orchestrator
  status:        open | accepted | fixed | wont-fix + why

 not verified” row in ADR-0004 stays that way.

Q2 — How is authentication handled, and how is my data kept from you?

Answer: self-rolled JWT with argon2, deliberately, and the isolation is the strongest thing in
 the codebase. Signup, login, refresh with single-use rotation and logout all exist
 (api/security/); refresh tokens are stored and revocable as rows; passwords are argon2-hashed;
 a boot guard refuses to start hosted on the development JWT secret.

Managed identity (Clerk, Auth0, Entra) was rejected in ADR-0004 and the choice stands, but it is not
 free: everything a provider would have handed over is now unbuilt work — password
 reset, email verification, MFA, session enumeration, brute-force lockout. A hosted product where a
 forgotten password is a permanent lockout is not shippable, which is why B1 email is a dependency of the
 deploy stage rather than a later nicety.

On the second half of the question — can I see someone else's data — the answer
 is the four-layer defence recorded as SEC-01: a ContextVar carries the org for the request,
 guard_tenant enforces it, every business table carries organization_id, and the
 repository layer scopes queries rather than trusting callers. The naive failure the reviewer looks for
 — GET /invoices/{id} loading by primary key and never comparing the org — does not
 occur here, and the tests assert it.

Where isolation stops. It is between organizations, not within one.
 Every member of an org is effectively an owner (SEC-11): a viewer can void an issued invoice and read
 every client record. That is the correlated critical finding in §18, and it
 is the honest answer to “only I can see my data” — true of tenants, not yet true of
 colleagues.

Q3 — What does this depend on, and what happens when a version goes end-of-life?

Answer: pinned and frozen, but nothing scans them and no one owns the upgrade clock.
 uv.lock holds 77 Python packages and CI installs frozen; npm audit and
 pip-audit are wired as advisory, deliberately — a gate hands a third party a veto
 over hotfix deploys. But CI has never run (Q1), so in practice SEC-14 is a gap: no scan has ever executed.

python ≥3.11 · Runtime
    Lifecycle exposure: Security support to late 2027; 3.11 is not the floor forever
    Risk: low

FastAPI · Pydantic 2 · uvicorn · HTTP boundary
    Lifecycle exposure: Fast-moving minors; no LTS. Pinned, upgraded by choice.
    Risk: low

SQLAlchemy 2.x · Alembic · Persistence
    Lifecycle exposure: A 3.x would be a real migration — but core/ never imports it, so the
    blast radius is db/ only
    Risk: medium

Chromium — the installed Edge, or Playwright's build · The PDF engine — the only one, since T-24. On Windows the desktop prints through the Edge already installed, from its own command line, with no Playwright in the runtime (T-21); the image ships Playwright's Chromium
    Lifecycle exposure: Browser pinning in the image (~1 GB); on the desktop, whatever Edge
    Windows Update left — so version drift changes rendering from two sides, and no
    golden-file test pins the output
    Risk: medium

(no XML library) · UBL / Peppol XML
    Lifecycle exposure: None — core/einvoicing/ writes and reads through xml.etree in the
    standard library. lxml was declared for a year and never imported; dropped in T-24.
    Risk: low

React 19 · Vite · TypeScript 5 · Frontends
    Lifecycle exposure: Ecosystem churn; three surfaces share one design system, so one
    upgrade moves all
    Risk: medium

Tauri · Desktop shell
    Lifecycle exposure: Rust toolchain + platform webview; the least-exercised surface
    Risk: medium

stripe, httpx · Outbound
    Lifecycle exposure: Stripe is a dependency with no call site yet — checkout is deferred
    (§16)
    Risk: low

Peppol Access Point · Outbound, contractual
    Lifecycle exposure: A reseller sets the per-document price, which sets the gross-margin
    floor
    Risk: the one vendor decision that prices the product

The structural answer to the end-of-life question is already in the architecture rather than in a policy
 document: core/ imports no framework. A FastAPI or SQLAlchemy major bump
 cannot reach the VAT engine, the numbering lock or the UBL builder, because dependencies point inward and
 never back out (ADR-0001). The upgrade surface is api/ and db/, and the 298
 domain tests keep running through it without a server or a database.

What is missing is not a scanner, it is an owner. Two things convert this table into
 an operational control: a remote so the advisory audits actually run, and a named review cadence
 — quarterly is enough at this size — whose output is a decision per row, not a report.
 A subprocessor list (P-09, CMP-05) falls out of the same review for free.

Q4 — What shape is the data, and in what formats?

Answer: overwhelmingly structured, with two semi-structured contracts and one unstructured
 category that has nowhere to live.

STRUCTURED — relational, the system of record
  organizations · users · memberships · credentials · refresh tokens
  companies · clients · products · invoices + lines · credit notes + lines
  payments · sequence counters · audit log · subscriptions
  Postgres (SaaS) │ SQLite (desktop) — same domain code, abstract ports

SEMI-STRUCTURED — contracts with the outside world
  UBL 2.1 / Peppol BIS 3.0 XML   core/einvoicing/  → validated, generated on demand
  JSON backup envelope           ADR-0003          → schema_version 1, restorable
  JSON over HTTP                 Pydantic in and out, openapi.json generated
  Legacy import payloads         core/imports/     → FinanceFlow parser, preview → commit

UNSTRUCTURED — no storage component exists (B2)
  Rendered PDFs        generated per request, never persisted
  Logos, attachments   no blob store
  Outbound email       no transport
  Logs                 structlog to a console, not retained anywhere

The load-bearing decision, and it is already the right one. The invoice
 domain object is the source of truth. The PDF and the Peppol XML are both renderings
 of it, produced on demand from the same validated data — neither is stored, so neither can drift
 from the record or become the record. Systems that persist the PDF and reconstruct meaning from it later
 cannot answer “what was invoiced” without parsing their own output. See
 §20, where this is the rule the document engine is built on.

Two consequences a reviewer should carry: nothing in the product currently stores a file, which
 is why every Documents-section gap in §14 resolves to one missing component rather
 than fifteen missing screens; and the audit log is structured relational data, not text, which is what
 makes it usable as fiscal evidence and as the Peppol-document meter (E-01).

Q5 — How sensitive is this to downtime and data loss, and is the deployment sized for it?

Answer: the targets have never been written down. Here they are, argued rather than assumed.

BillGen is not a bank and not an authenticator — nothing cascades into another product's
 availability. But it is not a content site either: an invoice has statutory deadlines, and a business that
 cannot issue at month-end has a real problem, not an inconvenience. The asymmetry that decides the numbers
 is that downtime is recoverable and data loss is not — a lost issued invoice breaks
 a gapless series that cannot legally be renumbered.

RTO — SaaS · 4 h
    Why that number: Within a working day. Month-end and quarter-end are the load-bearing
    dates; a morning of unavailability costs annoyance, a day costs a filing.
    Current capability: unmeasured — one VPS, redeploy by hand

RPO — SaaS · ≤5 min
    Why that number: Not hours. Any issued invoice lost after its number was minted leaves a
    gap in a legally gapless series — the one failure mode with no clean repair.
    Current capability: PITR is the reason ADR-0004 chose managed Postgres — not provisioned

RTO — desktop · user-paced
    Why that number: Reinstall plus restore from the JSON backup.
    Current capability: ADR-0003 export/restore ships

RPO — desktop · last backup
    Why that number: The SQLite file in the user's data directory is the only copy of the
    business's books. The user is the backup schedule, which means the product must nag.
    Current capability: manual export only — no reminder, no automatic copy

On the failover instance: no, and not yet. Active-active across regions at one node and
 one engineer buys a nine that nothing in this product needs, and costs a permanent complexity tax on every
 deploy. The correct posture at this scale is: managed Postgres with point-in-time recovery, off-box; an
 application tier that is a stateless image and can therefore be re-created on a new box from a tag; and
 object storage with versioning once B2 exists. That is a restorable system rather than a
 redundant one, and it meets a 4-hour RTO comfortably.

What matters far more than a second instance, and is genuinely absent:

RES-01 · Off-box database backups with PITR
    State: gap
    Note: The whole reason ADR-0004 pays for managed Postgres. Undecided on cost grounds —
    the open decision at the end of that ADR.

RES-02 · A rehearsed restore
    State: gap
    Note: A backup that has never been restored is a hypothesis. Restore into a scratch
    database, boot the API against it, issue one invoice, confirm the sequence continues.

RES-03 · Application-level export (ADR-0003)
    State: done
    Note: Org-scoped JSON, sequence counters verbatim, restore only into an empty org. A
    product feature — explicitly not a substitute for RES-01.

RES-04 · Reproducible infrastructure
    State: partial
    Note: Compose + Caddyfile + Dockerfile are in the repo; the box itself is hand-built and
    unbuilt.

RES-05 · Rollback path
    State: partial
    Note: Re-deploy the previous tag — which requires migrations to stay backward-compatible
    within a release pair. Nothing enforces that yet.

RES-06 · Desktop automatic local backup
    State: gap
    Note: VACUUM INTO on exit, kept as a rolling few copies. Cheap, and it removes the user
    from the backup schedule.

Q6 — How would you know something broke, before a customer tells you?

Answer: you would not. Observability today is structlog writing key-value
 lines to a console that nothing collects. ADR-0004 names the floor — Sentry plus a request-id
 middleware, with full OpenTelemetry deferred as team-scale overhead — and neither exists yet.

The signals worth having, in the order they become necessary: unhandled errors with a request id;
 liveness on the API and the database; failed logins and lockouts as security events rather than log
 lines (SEC-15); and then, as each component lands, the ones specific to this product — failed email
 sends, failed Peppol transmissions, failed payment webhooks, stuck recurring jobs. A failed Peppol
 transmission that nobody is told about is a legally undelivered invoice that the sender believes was
 delivered, which is the single most expensive silent failure in the system.

Q7 — How do you recover from an incident?

Answer: no procedure exists. Detection, containment, investigation, recovery, data
 verification, notification, post-mortem — none of it is written, and at solo-operator scale the
 procedure matters more than at team scale, because there is no second person to remember what to do.

Where this splits across two agents. AG-4 owns the technical capability — can
 the system be contained, restored and verified. AG-3 owns the legal consequence: a personal-data breach
 carries a notification obligation with a clock measured in hours, and the clock starts at awareness, not
 at resolution. A product with no detection (Q6) has a defensible-sounding but useless position: it will
 become aware late and be unable to evidence when. The two gaps compound.

The minimum honest version is one page: who is called, how the app is taken offline, where the backups
 are and how to restore one, how to confirm the restore is complete (invoice count, sequence counters, audit
 log continuity), what gets told to whom, and a template for writing down what happened. It is an afternoon
 of writing that only has value if it exists before the incident.

Document Engine
---------------

One engine, three document types, two renderings. Why “customizable invoice templates” is an architecture decision before it is a paid feature.

Today core/pdf/registry.py holds four Jinja templates chosen at render time by
 id — fr_standard, fr_detailed, nl_minimal,
 credit_note. That is a fixed catalogue in code: no organization can change one, and adding a
 fifth means shipping a release. The feature everyone means by “let me design my own invoice” is
 the thing that turns this catalogue into data.

The mistake to avoid, stated once. Do not build an invoice template editor. Build a
 document template engine and give it a type. Quotes, invoices and credit notes differ in their
 mandatory mentions, their totals block and their references — not in their layout system. Three
 editors means three places to fix a logo alignment bug and three places where a Belgian mandatory mention
 can go missing.

                    Invoice / CreditNote / Quote   ← domain object, source of truth
                                 │
                        validated document data
                                 │
                       ┌─────────┴─────────┐
                       ↓                   ↓
                  PDF renderer        UBL renderer
                   (Chromium)         (core/einvoicing)
                       ↓                   ↓
                    PDF file           Peppol BIS 3.0 XML
                       ↓                   ↓
                     email              access point

DocumentTemplate                     ← today: 4 rows of code. Target: a row per org.
  ├── type          QUOTE │ INVOICE │ CREDIT_NOTE
  ├── language      fr │ nl │ en │ de
  ├── layout, typography, logo, colours
  ├── sections and field visibility
  ├── conditional blocks   (reverse charge, intra-EU, deposit, discount)
  └── organization_id      ← what makes it customizable at all

DOC-01 · The PDF is never the source of truth
    Why: Both renderers read the same validated domain object. A template can change how an
    invoice looks and can never change what it says — which is also what keeps a customized
    template from producing a non-compliant document.

DOC-02 · Mandatory mentions are engine-level, not template-level
    Why: Belgian required elements — VAT numbers, exemption wording, reverse-charge notice,
    credit-note reference to its original — are injected and verified by the engine. A
    user-designed template may reposition them; it may not omit them. This is the single
    control that makes user-editable templates safe to sell.

DOC-03 · One template model, three types
    Why: The type selects which blocks are required and which are illegal; it does not
    select a different engine. Quotes are the type this repo does not yet have — adding them
    should be a type, not a subsystem.

DOC-04 · Templates are versioned and pinned per issued document
    Why: Re-rendering an invoice issued two years ago must reproduce the document as issued,
    not as the template looks now. The rendering is derived, but it must be reproducibly
    derived.

DOC-05 · One engine renders every document
    Why: There were two: Chromium on desktop and a GTK fallback in the image, which is two
    appearances for the same legally-binding document. ADR-0004 required a golden-file test
    proving they agreed before the fallback was relied on; the test was never written and
    the fallback never installed, so T-24 deleted it rather than the alternative. A per-org
    template surface is exactly why one engine is the cheaper answer. T-21 kept it one: the
    desktop prints through the installed Edge, which is Chromium, and each template's @page
    rule — guarded by a test — is the single source of page geometry for both launchers.

Where it sits commercially

The tier matrix (§16) already draws this line once:
 pdf_remove_branding is the free/paid boundary today, and the visual designer is its natural

Free · The shipped templates, branded footer. Credit notes and Peppol export included — correcting an invoice is not an upsell (E-03 reasoning).
    Matrix key: —

    Matrix key: pdf_remove_branding ✓ exists

    Matrix key: document_designer — not in the matrix yet

Sequencing. This is not next. The engine only becomes urgent once documents are

 the rendering path needs, and retrofitting per-org templates onto a persisted-PDF design would be the

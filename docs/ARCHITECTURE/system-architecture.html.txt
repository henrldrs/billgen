<section id="overview">
  <div class="sechead">
    <span class="sechead__id">§00</span>
    <h1>System Architecture</h1>
    <p class="sechead__sub">Audit of one product across four frontend surfaces, one Python backend, and a shared design system. Revised 2026-08-28 against commit <code>748fd2c</code> — the last <em>code</em> commit, since a document cannot name the commit that contains it.</p>
  </div>

  <p class="lede">BillGen is a Belgian invoicing SaaS with a finished domain core and an unfinished product wrapper. This document separates those two facts, measures each, and orders the work.</p>

  <div class="note">
    <p><strong>What changed since v0.10 (2026-08-27).</strong> Quotes shipped with their own numbering
    series, and the last report gaps closed — <code>/alerts</code>, <code>/search</code>,
    <code>/vat-treatment</code>, and the payments, clients and products reports. Two features were
    <em>scaffolded and deliberately left unwired</em> (<a href="#scaffolds">§18</a>), and a parallel
    audit engine was built from the specification in <code>docs/</code>
    (<a href="#audit">§19</a>). Backend tests 392 → <strong>423</strong>; the surface is now
    <span data-fact="endpoint_count">100</span> endpoints across
    <span data-fact="router_count">24</span> routers.</p>
    <p><strong>And this document stopped being hand-maintained where it kept going wrong.</strong> The
    audit engine found eight endpoints documented here that no longer existed and fifty that were never
    written down. The endpoint inventory and every volatile count are generated now
    (<a href="#audit">§19</a>); the judgements are not.</p>
  </div>

  <div class="grid g3">
    <div class="stat">
      <p class="stat__k">Product areas</p>
      <p class="stat__v">114</p>
      <p class="stat__n">leaf nodes in the IA · 130 with sections</p>
    </div>
    <div class="stat">
      <p class="stat__k">Fully wired</p>
      <p class="stat__v" style="color:var(--done)">26%</p> <p class="stat__n">30 wired · 26 partial · 58 none</p>
    </div>
    <div class="stat">
      <p class="stat__k">Missing capabilities</p>
      <p class="stat__v" style="color:var(--gap)">159</p> <p class="stat__n">distinct, over 83 nodes</p>
    </div>
    <div class="stat">
      <p class="stat__k">Library components</p>
      <p class="stat__v">74</p>
      <p class="stat__n">49 mounted · 25 never rendered</p>
    </div>
  </div>

  <div class="note">
    <p><strong>The central finding, restated.</strong> Layer 1 — the invoicing core — still has <em>zero</em> unwired areas. What has changed is the commercial half: it is no longer unstarted. The entitlement layer means the server can now price, meter and refuse, tier by tier. Nothing renders it yet. So the shape of the problem has moved from &ldquo;the backend cannot answer this&rdquo; to <strong>&ldquo;no screen asks&rdquo;</strong> — and that is frontend work, not architecture.</p>
  </div>

  <h3>What this document treats as source of truth</h3>
  <ul>
    <li><strong>The IA registry</strong> — <code>frontend-react/src/scaffold/ia.ts</code>, a typed tree that drives navigation, routes, status badges, and every count below. Invariants enforced by <code>ia.test.ts</code>.</li>
    <li><strong>The endpoint inventory</strong> — read directly from <code>api/routers/</code>, not from documentation. 17 routers, 55 endpoints as of <code>2a83ccb</code>.</li>
    <li><strong>The component matrix</strong> — computed by walking JSX across all frontends plus the Studio AI reference.</li>
    <li><strong>The Studio AI reference</strong> — <code>docs/billgen---enterprise-invoicing-&amp;-financial-saas.zip</code>, 95 files. A Google AI Studio (Gemini) generation dated 2026-08-25, seeded with this project&#39;s stylesheets but importing none of its components — see <a href="#repo">§15</a>.</li>
  </ul>

  <p>The reference makes a navigation pattern explicit that the current build only half implements. It has three depths, and each depth answers a different question:</p>

  <details>
    <summary>N1 — the sidebar decision that needs making</summary>
    <div class="det-body">
      <p>The reference uses a persistent dark sidebar with 11 destinations grouped under <em>Menu Principal</em> and <em>Configuration &amp; Fiscalité</em>, each carrying a count badge (overdue invoices, quote count, customer count).</p>
      <p>The current build deliberately deleted its sidebar in favour of TopNav-only navigation with five destinations. Both are defensible; they are not compatible. The reference's model scales to the 15-section IA far better, and the count badges are real signal. Adopting it means reversing the earlier decision, which is a product call.</p>
      <p><code>SidebarNav</code> exists in the library with <code>category</code> and <code>badge</code> support already in its props — so the component cost of switching is close to zero.</p>
    </div>
  </details>

  <details>
    <summary>N2 — what the section sub-navigation should carry per section</summary>
    <div class="det-body">
      <p>Invoices already does this correctly: six status tabs, each with a count, backed by the server-side <code>?status</code> filter. The pattern generalises:</p>
      <ul>
        <li><strong>Sales → Invoices</strong> — Toutes / Brouillons / Émises / Payées / Partiellement payées / En retard / Annulées <span class="chip c-done">built</span></li>
        <li><strong>Sales → Quotes</strong> — All / Draft / Sent / Accepted / Refused / Expired / Invoiced <span class="chip c-gap">no backend</span></li>
        <li><strong>Clients</strong> — All / Active / Archived / Missing VAT / Missing address <span class="chip c-gap">needs filters</span></li>
        <li><strong>Catalog</strong> — Products / Services / Categories / Pricing / VAT / Archived <span class="chip c-partial">derivable, unfiltered</span></li>
        <li><strong>Reports</strong> — Revenue / Invoices / Payments / Outstanding / Overdue / VAT / Export <span class="chip c-partial">3 of 7 wired</span></li>
        <li><strong>Settings</strong> — the <code>SettingsShell</code> rail, 15 sections <span class="chip c-partial">rail built, sections stubbed</span></li>
      </ul>
      <p>Counts on N2 tabs must come from the server. Computing them by fetching every record and counting in the browser works at demo scale and fails at customer scale.</p>
    </div>
  </details>

  <details>
    <summary>N3 — the record inspector, currently missing entirely</summary>
    <div class="det-body">
      <p>The reference implements <code>InvoiceDrawer</code> and <code>CustomerDrawer</code>: a right-hand panel carrying identity, status badge, metadata, financials, copyable identifiers, a status timeline, and the action cluster.</p>
      <p>This is the single highest-value structural pattern in the reference, because it also solves the "action soup" problem — five equal-weight buttons per table row move into the drawer, and the row keeps one primary action plus an overflow menu.</p>
      <p><code>Drawer</code>, <code>StatusTimeline</code>, <code>CopyButton</code>, <code>ConfirmDialog</code> and <code>Menu</code> are all built and none are rendered anywhere in the shipping app.</p>
    </div>
  </details>

  <details>
    <summary>Why Peppol is the highest-leverage compliance item</summary>
    <div class="det-body">
      <p>Belgium mandates structured e-invoicing for B2B from 2026. BillGen already produces Helger-validated Peppol BIS 3.0 XML carrying the Belgian elements — EndpointIDs, OGM-VCS structured communication, KBO legal identifier, party contact — layered over the EN 16931 multi-rate engine.</p>
      <p><strong>Every part of that is done and none of it ships.</strong> The file is generated and downloaded by hand because no Access Point transmits it. This is the one place where a single integration converts finished, tested work into a headline market capability. It is not a settings toggle; treat it as a product surface.</p>
      <p><strong>State the gap precisely, because this document has stated it loosely.</strong> The open
      question is <em>not</em> whether the XML is correct — the predecessor demo's PDF → Peppol path was
      exercised with a real user, and schematron passes here on BE and non-BE samples. The gap is
      <strong>transmission from inside the application</strong>: sending over the network the way a bank's
      billing app does, rather than producing a file a human then hands to a portal like Doccle. Those are
      different products to the person using them, and only the second one exists today.</p>
      <p>Two things that follow, and neither is a coding task. <strong>You do not have to be an Access
      Point.</strong> Resellers (Storecove, Ecosio, Unifiedpost) turn an existential interoperability risk
      into a procurement decision — and their per-document price then sets the gross-margin floor, which
      means it sets BillGen's price. <strong>Onboarding one is calendar-bound, not code-bound:</strong> a
      contract, KYC, SMP registration and a company number, measured in weeks of somebody else's queue. It
      is therefore a clock to start in parallel with everything on the roadmap below, and it cannot be
      sequenced after any of it.</p>
    </div>
  </details>

  <details>
    <summary>Cookie consent — currently compliant by accident</summary>
    <div class="det-body">
      <p>No analytics run anywhere in the product today. That is the only reason the absence of a consent mechanism is not already a violation. The moment any analytics, session recording, or marketing pixel is added, <code>CMP-04</code> becomes blocking rather than pending.</p>
      <p>Build the consent layer <em>before</em> the first analytics call, not after.</p>
    </div>
  </details>

    <p class="sechead__sub">The layers that are invisible from the frontend. Not a checklist to tick once &mdash; the set of properties a new feature must not break.</p>
  </div>

  <div class="note">
    <p><strong>Why this section exists, and why it is not a checkbox list.</strong> The naive model of a web application is two boxes: frontend, backend. The real one is closer to <strong>thirty-seven</strong>, and eleven of the original thirteen are invisible from the screen &mdash; which is exactly why they are discovered late, after a customer, and expensively.</p>
    <p>Every row below is a <em>property of the system</em>, not a task. The failure mode this section prevents is not ignorance of the rows. It is finishing the frontend and the API, feeling done, and meeting PROD-01 and PROD-06 the week after the first customer's data goes missing.</p>
    <p class="muted">Cross-checked against OWASP Top 10:2025, OWASP ASVS 5.0, Twelve-Factor, AWS Well-Architected, Google SRE, DORA and ISO/IEC 25010:2023. Per-item verification tests live in <code>docs/MINIMAL_STACK.md</code>; the AI Act rows are argued in <code>ADR-0005</code>.</p>

  <h3>Tier</h3>
  <p>BillGen is <strong>T3 &mdash; regulated</strong>. Not aspirationally: it issues fiscal documents under a seven-year Belgian retention obligation, processes personal data belonging to its customers' customers, and ships AI-bearing features into the EU.   <div class="warn">
    <p><strong>How to use this section when adding a feature.</strong> These rows are guardrails, so the question is never &ldquo;have I ticked them&rdquo; but &ldquo;does what I am about to build break one&rdquo;:</p>
    <ul>
      <li><strong>Does it read or write data?</strong> It goes through a repository port. Not for tidiness &mdash; that port is what makes SEC-01 and SEC-17 true, and a raw-SQL shortcut silently repeals both at once.</li>
      <li><strong>Does it take longer than a request should, or call anyone external?</strong> It needs PROD-07, which does not exist yet. Say so, rather than putting it in a handler.</li>
      <li><strong>Does a machine produce output a person reads?</strong> It enters the <code>ai_transparency</code> registry <em>before</em> it ships, with its tier and its drift path (AI-01, AI-02).</li>
      <li><strong>Does it score a person rather than classify a transaction?</strong> Stop. That is Annex III, a conformity assessment, and a different product timeline (AI-05).</li>
      <li><strong>Does it add a dependency, a secret, or an environment variable?</strong> SEC-13 and SEC-14 &mdash; and the field exists in <code>Settings</code> before it appears in <code>.env.example</code>, never the other way round.</li>
      <li><strong>Does it store personal data, or a new kind of document?</strong> <code>core/trust/personal_data.py</code> gains a row with a purpose, a basis and a retention, or SEC-12 gets quietly worse.</li>
    </ul>
    <p class="muted">A status in this section with no evidence &mdash; a path, a command, an endpoint &mdash; is an opinion, not a status. And staleness runs both ways: six rows above described a <em>weaker</em> system than the one that exists, which is how a downstream analysis inherits a defect that was already fixed.</p>
  </div>

  <h3>Reading the diagram</h3>
  <p>The load-bearing claim is band 2. <code>ia.ts</code> is not documentation — it is a typed registry that the router, the navigation and the status badges all read at runtime. A product area that is not a node in that file cannot be reached in any frontend, and a node marked anything other than <code>wired</code> renders through the deliberately-ugly scaffold kit so unbuilt surface can never be mistaken for finished work.</p>

  <p>Bands 3 to 5 are the rule the whole backend is organised around, recorded in <a href="ADR-0001-three-layer.md">ADR-0001</a>: <strong>dependencies point inward and never back out.</strong> <code>core/</code> imports no framework — no FastAPI, no SQLAlchemy — which is why the 298 tests run without a server or a database. <code>api/</code> may import <code>core/</code>; <code>core/</code> may not import <code>api/</code>. Persistence is reached through abstract ports in <code>core/repository/</code>, which is what lets the same domain code run against SQLite on the desktop and Postgres in the cloud.</p>

  <p>The two facts worth carrying away from band 6: nothing in the product sends anything to anyone, and nothing stores a file. Every gap that looks like a missing screen in §14 resolves to one of those four boxes.</p>

  <div class="note note--warn">
    <p><strong>The path that stops short.</strong> Follow the Peppol rail. <code>core/einvoicing/ubl_builder</code> produces BIS 3.0 XML that passes Helger validation, <code>GET /invoices/{id}/peppol.xml</code> serves it, and the user downloads a file. In a finished product that file is transmitted to an access point and the invoice is legally delivered. Here the flow ends at the browser's download folder. The engineering is done; the last hop was never built.</p>
  </div>

  <h3>The four design decisions worth keeping</h3>

  <div class="tw">
    <table>
      <thead><tr><th class="id">#</th><th>Decision</th><th>Why it is built this way</th></tr></thead>
      <tbody>
        <tr><td class="id">E-01</td><td><strong>Usage is derived, never accumulated</strong></td><td class="ev">Every meter is a <code>COUNT(*)</code> over rows that already exist, filtered on <code>created_at</code> for flow meters.   <details>
    <summary>The concurrency guard, and the one thing it has not proven</summary>
    <div class="det-body">
      <p><code>quota_guard</code> is a context manager that takes a row lock on the organization <em>before</em> counting and holds it until the endpoint body's own transaction has landed. Without it the naive shape — read 49, return, create, and someone else also read 49 — lets two concurrent requests both create the 50th invoice. Every quota check for one tenant serialises on that single row; different tenants never contend.</p>
      <p class="lede" style="font-size:15px"><strong>It is unproven.</strong> <code>with_for_update()</code> is a no-op on SQLite — one connection behind a <code>StaticPool</code>, which is what both the desktop build and the entire test suite run on. It becomes a real <code>FOR UPDATE</code> only on Postgres. The CI workflow runs the Python suite twice, once on each, and <strong>CI has never executed</strong> because the repo has never been pushed (<code>BGEN-OPS-01</code>). The same asymmetry, for the same reason, applies to the gapless numbering lock. A red first run would be information, not a regression.</p>
    </div>
  </details>

When roles are enforced they must also be gated, since <code>roles_permissions</code> is Business+ — the two have to land together or the enforcement leaks a paid feature to Free.</p>
  </div>

  <div class="note note--stop">
    <p><strong>The one legal item that cannot be coded around.</strong> The downgrade and lapsed-subscription <em>behaviour</em> is settled and tested (E-03: keep every record, refuse only new creation). The downgrade <em>contract</em> — how long data is retained after cancellation, and on what basis — belongs in the DPA, and the DPA does not exist (<code>CMP-10</code>). No cancellation flow should be built before it does.</p>
  </div>

<section id="decisions">
  <div class="sechead">
    <span class="sechead__id">&#167;17</span>
    <h2>Decisions of Record</h2>
    <p class="sechead__sub">Four rulings this document had no section for. The board is <code>ROADMAP_IA.md</code>; this is the summary an architecture reader needs.</p>
  </div>

  <p class="lede">Three were taken on 2026-08-27 and one is the correction that produced them. They are here
  because each one changes how a number elsewhere in this document should be read.</p>

  <h3>&#167;11b &mdash; the navigation is not the coverage map</h3>
  <p>Until this session, <code>routableNodes()</code> generated the router straight from <code>ia.ts</code>,
  so <em>a node exists</em> and <em>a node is a destination</em> were one statement. That was correct while
  the product was half-built: <code>SectionIndex</code> counting wired areas and <code>ScaffoldPage</code>
  naming the endpoint each gap waits for are <strong>build-time instruments</strong>, and they earned their
  place. They stop earning it as the gaps close. Company was the proof &mdash; nine nav entries over one
  <code>PATCH</code> against one row.</p>

  <div class="note">
    <p><strong>The rule.</strong> A nav destination is a place you go <em>before</em> you know which record
    you want. Anything that only means something <em>after</em> you have picked one belongs inside that
    record. Not &ldquo;remove the repetition&rdquo; &mdash; repetition is the symptom; the cut is list vs
    record.</p>
  </div>

  <p><strong>The mechanism, and why it does not move any number above.</strong> <code>IaNode</code> gained
  <code>nav?: boolean</code> and <code>mergedInto?: string</code>. A hidden node keeps its path, its status
  and its place in <code>coverage()</code>; it loses only the door, and <code>mergedInto</code> makes the old
  URL redirect rather than 404. <code>routableNodes()</code>, <code>coverage()</code> and
  <code>missingEndpoints()</code> still read the whole tree, which is why <a href="#status">&#167;01</a>
  counts 114 leaves with 15 of them curated out of the nav. A guard test asserts exactly that: curating must
  never change a coverage number.</p>

  <p><strong>Applied to two sections, proposed for ten.</strong> Company is 9 entries &rarr; 1 (the section
  landing <em>is</em> the record, and the three areas blocked on a model are scaffold blocks inside it).
  Clients is 7 &rarr; 3. The remaining sections have a written proposal in &#167;11b &mdash; roughly 100 nav
  entries down to 45 &mdash; and are built by nobody pending a decision.</p>

  <p class="warn"><strong>What the rule caught on its first day.</strong> &ldquo;Client 360&rdquo; was a
  Clients menu entry whose path is <code>customers/clients/:clientId</code>, so clicking it navigated to that
  literal string. Invoice detail was the same, and the command palette had the bug one layer down. Nobody had
  noticed, because the way to a record is to click a row &mdash; which is the rule, arriving as a bug before
  it arrived as a principle.</p>

  <h3>&#167;11c &mdash; comments must not ship, and must not be deleted</h3>
  <p>The published artifact should not read as a guided tour of how the product works; the comments are also
  the reason a session can resume where the last one stopped. So: <strong>strip on export, never in the
  tree.</strong> The exposure is narrower than it looks &mdash; a private repo is unreadable, and the SaaS
  bundle is already clean because Vite minifies with esbuild and ships no sourcemap. The Electron artifact is
  the real one: <code>app.asar</code> unpacks trivially, and a bundled Python backend is source.</p>
  <p><strong>The trap:</strong> docstrings here are not comments. FastAPI and Pydantic publish them &mdash; a
  class docstring becomes the OpenAPI <code>description</code>, which generates <code>api.d.ts</code>. Strip
  <code>#</code> comments freely; spare schema and route docstrings or the API documents itself into silence.</p>

  <h3>&#167;11d &mdash; what &ldquo;safely deletable&rdquo; means in this tree</h3>
  <p>Three jobs keep being bundled and belong apart: <em>not writing the code</em> (a write-time discipline),
  <em>finding what is genuinely unused</em> (<code>knip</code> / <code>vulture</code> &mdash; zero tokens,
  objective, repeatable), and <em>keeping comments out of the artifact</em> (&#167;11c). An over-engineering
  audit pointed at this tree will flag the instruments the project is steered by: the scaffold kit, the
  never-rendered components, IA nodes with no screen, the comments, and four languages with a key guard but
  no usage guard. A deletion is safe when the guard tests stay green <em>and</em> the deleted thing is not one
  of those five.</p>

  <h3>Peppol &mdash; the gap is transmission, not validation</h3>
  <p>Corrected 2026-08-27, and it changes how <a href="#compliance">&#167;08</a> reads. The XML is not the open
  question: the predecessor demo's PDF &rarr; Peppol path was exercised with a real user, and schematron
  passes here. What does not exist is <strong>sending from inside the application</strong> rather than handing
  a file to a portal. You do not need to <em>be</em> an Access Point &mdash; reselling one turns the
  interoperability risk into procurement, and that vendor's per-document price sets this product's price
  floor. Onboarding is contractual and measured in weeks, so it is a clock to start in parallel with the
  roadmap, never a step sequenced after it.</p>
</section>

  <h3>The order, if money were spent tomorrow</h3>
  <ol>
    <li><strong>DevOps &mdash; bought, not hired.</strong> Nine open rows, and most of PROD-01 to PROD-04 are managed services costing tens of euros a month. Highest risk removed per euro, by a wide margin.</li>
    <li><strong>The jurist, for the DPA and terms.</strong> Blocks B2B revenue outright. Cannot be engineered around.</li>
    <li><strong>The accountant, for the mandatory-mention sign-off.</strong> The gate is live in <code>issue()</code> and is a legal claim the code cannot self-certify.</li>
    <li><strong>The Peppol Access Point conversation.</strong> Not because it is urgent, but because it is <em>slow</em> &mdash; the queue starts when you join it.</li>
    <li><strong>Marketing content.</strong> The mandate creates the demand; someone has to meet it in writing.</li>
  </ol>

  <div class="warn">
    <p><strong>The failure mode this section is really about.</strong> A solo founder does not drop roles they have decided to skip. They drop the roles they never named &mdash; and the named-but-unowned rows above (DevOps, legal, compliance, partnerships) are precisely the ones with no daily feedback. Nothing on a screen goes red when there is no rehearsed restore. The frontend, by contrast, complains the moment it is neglected, so it gets the attention.</p>
    <p>That asymmetry is why this document appears static beside the frontend: <strong>the visible layer reports its own state and the invisible ones do not.</strong> The remedy is not discipline &mdash; it is making the invisible rows produce evidence, which is what &#167;10 and the audit engine exist to do. A row here with no name against it is a decision, and it should be a deliberate one.</p>

  <div class="warn">

    <p>That is a more useful finding than any completeness score, because it is one decision &mdash; pick a transactional mail provider &mdash; that unblocks five stages at once. It also needs PROD-07, a job queue, because mail does not belong in a request handler.</p>

  <h3>Two clocks that start without you</h3>
  <p>Most gaps above wait politely. These two do not &mdash; they begin on someone else's action, and the countdown runs whether or not anything is built:</p>
  <ul>
    <li><strong>Erasure &mdash; one month</strong> from a customer's request (J-14). Extendable to three with justification, but the extension itself must be communicated inside the first month.</li>
    <li><strong>Breach notification &mdash; 72 hours</strong> from awareness. <span class="chip c-none">none</span> There is no incident-response plan, no notification template, and no defined &ldquo;aware&rdquo; moment. Note the dependency: <em>awareness requires detection</em>, and detection is PROD-01 and PROD-04. Without them the 72 hours start whenever someone happens to notice &mdash; which is not a defence, it is a longer breach.</li>
  </ul>

  <div class="note">
    <p><strong>Being honest about the order.</strong> Nothing in this section argues for building J-04 through J-12 before hosting exists. It argues that the gap is <em>known and shaped</em>, not diffuse &mdash; and that &ldquo;what does a paying customer need&rdquo; is a different question from &ldquo;what does a 50-person company need&rdquo; (&#167;21). Both are worth answering. Only one of them is between here and the first euro.</p>
  </div>

  <h3>Reading the layers</h3>
  <p>Each layer may import only from the ones below it. <code>api/</code> reaching into
  <code>db/</code> is allowed and deliberate — the HTTP layer builds the unit of work that

  appear is an arrow pointing <em>down</em> out of <code>core/</code>.</p>

  <p><code>billgen-audit/</code> appears in the directory table and in no layer, which is
  correct: it is a parallel project that reads this repository as text and is imported by

(() => {
  "use strict";

  /* ------------------------------------------------------------- theme
     Light is the default. A stored choice wins; otherwise the OS
     preference decides once, and clicking pins it. */
  const root = document.documentElement;
  const stored = (() => { try { return localStorage.getItem("billgen-arch-theme"); } catch { return null; } })();
  const prefersDark = window.matchMedia && window.matchMedia("(prefers-color-scheme: dark)").matches;
  root.setAttribute("data-theme", stored || (prefersDark ? "dark" : "light"));

  const tt = document.getElementById("tt");
  tt.addEventListener("click", () => {
    const next = root.getAttribute("data-theme") === "dark" ? "light" : "dark";
    root.setAttribute("data-theme", next);
    try { localStorage.setItem("billgen-arch-theme", next); } catch {}
  });

  /* --------------------------------------------------- the active card
     One card in the rail, kept in sync with what is on screen. The full
     list stays available behind the toggle for jumping across the doc. */
  const links = Array.from(document.querySelectorAll("#rail-list a"));
  const groups = new Map();
  let group = "";
  for (const node of document.getElementById("rail-list").children) {
    if (node.classList.contains("rail__group")) group = node.textContent;
    else if (node.tagName === "A") groups.set(node.getAttribute("href").slice(1), group);
  }

  const sections = links
    .map((a) => document.getElementById(a.getAttribute("href").slice(1)))
    .filter(Boolean);

  const el = {
    group: document.getElementById("nc-group"),
    id: document.getElementById("nc-id"),
    pos: document.getElementById("nc-pos"),
    title: document.getElementById("nc-title"),
    sub: document.getElementById("nc-sub"),
    bar: document.getElementById("railbar"),
  };

  let current = -1;

  const render = (i) => {
    if (i === current || i < 0 || i >= sections.length) return;
    current = i;
    const s = sections[i];
    const head = s.querySelector(".sechead");
    el.group.textContent = groups.get(s.id) || "";
    el.id.textContent = head?.querySelector(".sechead__id")?.textContent || "";
    el.title.textContent = head?.querySelector("h1, h2")?.textContent || s.id;
    el.sub.textContent = head?.querySelector(".sechead__sub")?.textContent || "";
    el.pos.textContent = (i + 1) + " / " + sections.length;
    el.bar.style.width = (((i + 1) / sections.length) * 100).toFixed(1) + "%";
    links.forEach((a, n) => a.classList.toggle("is-active", n === i));
  };

  /* Scroll position, not intersection ratio: with sections this tall the
     one crossing a line a third down the viewport is the one being read. */
  const spy = () => {
    const line = window.scrollY + window.innerHeight * 0.3;
    let i = 0;
    for (let n = 0; n < sections.length; n++) {
      if (sections[n].offsetTop <= line) i = n;
    }
    render(i);
  };

  let ticking = false;
  window.addEventListener("scroll", () => {
    if (ticking) return;
    ticking = true;
    requestAnimationFrame(() => { spy(); ticking = false; });
  }, { passive: true });
  window.addEventListener("resize", spy, { passive: true });
  spy();
  render(current < 0 ? 0 : current);

  const go = (i) => {
    const n = Math.max(0, Math.min(sections.length - 1, i));
    sections[n].scrollIntoView({ behavior: "smooth", block: "start" });
  };
  document.getElementById("nc-prev").addEventListener("click", () => go(current - 1));
  document.getElementById("nc-next").addEventListener("click", () => go(current + 1));

  const surfaceBtn = document.getElementById("surface-btn");
  const surfaceMenu = document.getElementById("surface-menu");
  if (surfaceBtn && surfaceMenu) {
    const close = () => {
      surfaceMenu.hidden = true;
      surfaceBtn.setAttribute("aria-expanded", "false");
    };
    surfaceBtn.addEventListener("click", (event) => {
      event.stopPropagation();
      const open = surfaceMenu.hidden;
      surfaceMenu.hidden = !open;
      surfaceBtn.setAttribute("aria-expanded", String(open));
    });
    document.addEventListener("click", (event) => {
      if (!surfaceMenu.hidden && !surfaceMenu.contains(event.target)) close();
    });
    document.addEventListener("keydown", (event) => {
      if (event.key === "Escape") close();
    });
  }

  const toggle = document.getElementById("rail-toggle");
  const list = document.getElementById("rail-list");
  toggle.addEventListener("click", () => {
    const open = toggle.getAttribute("aria-expanded") === "true";
    toggle.setAttribute("aria-expanded", String(!open));
    list.hidden = open;
  });
  /* Picking a destination collapses the list again — the card takes over. */
  list.addEventListener("click", (e) => {
    if (e.target.closest("a")) {
      toggle.setAttribute("aria-expanded", "false");
      list.hidden = true;
    }
  });
})();
</script>

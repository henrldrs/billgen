System Architecture

Audit of one product across four frontend surfaces, one Python backend, and a shared design system. Generated 2026-08-25 against commit 9984869.

BillGen is a Belgian invoicing SaaS with a finished domain core and an unfinished product wrapper. This document separates those two facts, measures each, and orders the work.

The central finding. Layer 1 — the invoicing core — has zero unwired areas. Everything outstanding is the SaaS wrapper around it. The engineering half of the 2026 audit closed; the commercial half never started. That is a coherent position to be in, and it is not the same as being 18% finished.

What this document treats as source of truth

  • The IA registry — frontend-react/src/scaffold/ia.ts, a typed tree that drives navigation, routes, status badges, and every count below. Invariants enforced by ia.test.ts.
  • The endpoint inventory — read directly from api/routers/, not from documentation.
  • The component matrix — computed by walking JSX across all frontends plus the Studio AI reference.
  • The Studio AI reference — docs/billgen---enterprise-invoicing-&-financial-saas.zip, 95 files, built on top of this project's own component library.

The multi-layer navigation model

The reference makes a navigation pattern explicit that the current build only half implements. It has three depths, and each depth answers a different question:

DepthQuestion it answersMechanismState
N1 PrimaryWhich part of the business am I in?Sidebar rail, 11 destinations in two labelled groups, each with a live count badgepartial
N2 SectionWhich slice of this section?Per-page sub-navigation: Tabs with counts on lists, SettingsShell rail on settingspartial
N3 RecordWhat is true of this one record?Drawer inspector — metadata, financials, StatusTimeline, actionsgap
N1 — the sidebar decision that needs making

The reference uses a persistent dark sidebar with 11 destinations grouped under Menu Principal and Configuration & Fiscalité, each carrying a count badge (overdue invoices, quote count, customer count).

The current build deliberately deleted its sidebar in favour of TopNav-only navigation with five destinations. Both are defensible; they are not compatible. The reference's model scales to the 15-section IA far better, and the count badges are real signal. Adopting it means reversing the earlier decision, which is a product call.

SidebarNav exists in the library with category and badge support already in its props — so the component cost of switching is close to zero.

N2 — what the section sub-navigation should carry per section

Invoices already does this correctly: six status tabs, each with a count, backed by the server-side ?status filter. The pattern generalises:

  • Sales → Invoices — Toutes / Brouillons / Émises / Payées / Partiellement payées / En retard / Annulées built
  • Sales → Quotes — All / Draft / Sent / Accepted / Refused / Expired / Invoiced no backend
  • Clients — All / Active / Archived / Missing VAT / Missing address needs filters
  • Catalog — Products / Services / Categories / Pricing / VAT / Archived derivable, unfiltered
  • Reports — Revenue / Invoices / Payments / Outstanding / Overdue / VAT / Export 3 of 7 wired
  • Settings — the SettingsShell rail, 15 sections rail built, sections stubbed

Counts on N2 tabs must come from the server. Computing them by fetching every record and counting in the browser works at demo scale and fails at customer scale.

N3 — the record inspector, currently missing entirely

The reference implements InvoiceDrawer and CustomerDrawer: a right-hand panel carrying identity, status badge, metadata, financials, copyable identifiers, a status timeline, and the action cluster.

This is the single highest-value structural pattern in the reference, because it also solves the "action soup" problem — five equal-weight buttons per table row move into the drawer, and the row keeps one primary action plus an overflow menu.

Drawer, StatusTimeline, CopyButton, ConfirmDialog and Menu are all built and none are rendered anywhere in the shipping app.

Token divergence — a decision, not a bug

Decided 2026-08-25 — tokens.css is the standard. The reference kept --brand-emerald-500 in the palette but repointed --bg-accent at --brand-blue-500 #2563EB, and swapped Satoshi for Plus Jakarta Sans. That re-skin is rejected: emerald #10B981 and Satoshi remain canonical, and the reference contributes layout and component patterns only — never palette or type.

Enforced rather than documented: frontend-react/src/scaffold/tokens.test.ts fails the build if the accent stops being emerald, the sans face stops being Satoshi, or any Tailwind colour utility or raw hex reaches app or component source. The four violations that existed — text-blue-700 and text-gray-500 on the auth screens — are fixed.

Dependency comparison — what the reference pulls in that we should not
  • @google/genai — an AI SDK with no corresponding UI in the reference. Dead weight; do not adopt.
  • canvas-confetti — celebratory micro-interaction. Optional; costs 4 KB.
  • motion 12.x — the current system does motion in CSS tokens. Adding a JS animation library duplicates that.
  • lucide-react — worth considering only as a wholesale replacement for the 14 custom icons, not alongside them.
  • express — the reference serves itself; irrelevant here, the API is FastAPI.
  • No router and no state library. The reference switches views with useState. The SaaS app uses react-router and TanStack Query — strictly better; do not regress.

Already-solved logic that is trapped behind a missing endpoint

These are the cheapest wins on the board — the Python exists and works, only the HTTP surface is absent.

  • core/rules/vat.py — Belgian VAT categories and rate construction. No GET /vat-rates, so the frontend hardcodes 21/12/6/0. That is a correctness risk, not a convenience gap.
  • core/pdf/registry.TEMPLATES — four templates. No GET /pdf-templates, so a template picker cannot be populated.
  • core/rules/identifiers.py — VAT mod-97, IBAN ISO 13616, BIC ISO 9362 checksums, ported from the approved demo. No validation endpoint, so the UI cannot check a VAT number before submit.
  • core/repository/sequence_repo — the gapless counter. Not readable, so "next invoice number" cannot be shown in settings.
  • core/einvoicing/ubl_builder — Helger-validated BIS 3.0 XML. Generated and downloaded by hand; nothing transmits it.

Why Peppol is the highest-leverage compliance item

Belgium mandates structured e-invoicing for B2B from 2026. BillGen already produces Helger-validated Peppol BIS 3.0 XML carrying the Belgian elements — EndpointIDs, OGM-VCS structured communication, KBO legal identifier, party contact — layered over the EN 16931 multi-rate engine.

Every part of that is done and none of it ships. The file is generated and downloaded by hand because no Access Point transmits it. This is the one place where a single integration converts finished, tested work into a headline market capability. It is not a settings toggle; treat it as a product surface.

Round-trip through a real Access Point remains untested — schematron validation has passed on BE and non-BE samples, which is necessary and not sufficient.

Cookie consent — currently compliant by accident

No analytics run anywhere in the product today. That is the only reason the absence of a consent mechanism is not already a violation. The moment any analytics, session recording, or marketing pixel is added, CMP-04 becomes blocking rather than pending.

Build the consent layer before the first analytics call, not after.

Possible Features & Extensions

Beyond the IA. Recorded so they are choices rather than surprises.

Belgian market depth
  • Quarterly VAT return pre-filled and exportable to Intervat
  • Client listing (annual customer listing) — a legal obligation
  • Intracommunity statement for EU B2B
  • Accountant role with scoped export-only access
  • Statutory late-interest calculator on reminders
  • Mandatory-mention checker per language before issue
Admin / back-office (a separate product)

Not in the customer IA and should never be. Organizations, subscriptions, revenue, usage, support tickets, security events, system health, feature flags, failed payments, audit logs.

Shares the design system and backend; separate shell, separate auth boundary.

Public marketing site

Pricing, signup, changelog, status page, and the legal corpus. Note that Legal and System status appear in both the app and the public site — write once, mount twice.

Client-facing invoice portal

A public per-invoice page. Prerequisite for the Viewed status, and the natural home for online payment. Turns two dead lifecycle states into real ones.

Bank reconciliation

CODA import matched against the OGM-VCS structured communication already generated per invoice. The matching key exists — this is closer than it looks.

Deliberately out of scope
  • Inventory / stock management — a different product
  • Payroll — heavily regulated, separate compliance surface
  • Full double-entry bookkeeping — export to the accountant instead
  • Native iOS/Android — responsive web first; revisit after V1
§12

Workflow Starter

The next five moves, in order.

STEP 1Ship PATCH /companies/{id}

One endpoint. Converts six Company areas from write-once to editable, and removes the most visible defect in the product — a permanent VAT typo. Every field already exists on the model. See §04, BGEN-API-01.

STEP 2Expose the rules that already exist

GET /vat-rates, GET /pdf-templates, identifier validation. Pure plumbing over finished Python, and it removes hardcoded VAT rates from the frontend — a correctness risk, not a convenience. See §04, BGEN-API-04.

STEP 3Build the VAT report

The highest user value available. For the target customer this is the reason to own the software, and every input is already in the database. See Sprint 2.

STEP 4Start email transport (B1)

Longest lead time and widest fan-out, so start it early and in dependency order: provider → password reset → verification → send-invoice → reminders. See Sprint 3.

STEP 5Settle the three open decisions

These are cheap now and expensive later, because everything built afterward inherits them:

  • BGEN-BRAND-01 — decided: tokens.css is the standard, emerald + Satoshi stay
  • BGEN-BRAND-02 — sidebar (11 destinations, reference) or TopNav-only (5, current)?
  • BGEN-BRAND-03 — one icon grammar: custom SVG, lucide, or emoji. Not three.

In parallel, blocking nothing: the L6 experience list is entirely frontend and depends on no endpoint. Items L6-01 through L6-03 — panel styling, heading weight, button contrast — are hours of work and change the perceived quality of every screen in the product.

Then push the repo. BGEN-OPS-01: the CI workflow has been written and waiting since dd0483e, and the entire history is still local-only. Every gate above assumes work that is backed up and continuously tested.
